# 《七大奇迹对决》数字化实现方案

> 版本：v1.0（方案阶段，不输出实现代码）  
> 目标：在本地热座、人机、联机三种模式下，完整复现基础版《七大奇迹对决》规则，并保证规则引擎、状态机、结算逻辑被三者复用。

---

## 1. 项目背景与现有资料

### 1.1 现有文件

`docs/rules/` 现有 5 份 PDF，均为规则与参考材料：

| 文件名 | 用途 | 说明 |
|---|---|---|
| `7-Wonders-Duel-Rules-US.pdf` | 官方英文规则书（20 页） | **基础版规则唯一权威来源** |
| `7-Wonders-Duel-Reference-Card-v4.pdf` | 双面对开参考卡 | 回合流程、贸易公式、科技胜利条件速查 |
| `7_Wonders_Duel_Complete_Reference_Sheet_V4.pdf` | 四页完整参考表 | 含基础 + 扩充（Pantheon / Agora）内容，数据录入时需排除扩充 |
| `7_Wonders_Duel_Rules_Help_Sheets.pdf` | 帮助表 | 主要为 Pantheon、Agora 扩充机制说明 |
| `7_Wonders_Duel_Sheets_ver_2.pdf` | 计分纸 | 终局计分格式参考 |

### 1.2 现有技术栈

- 代码：无。
- 可用运行时：Node.js 22.22.2、Python 3.13.12。
- 仓库：未初始化 Git。

### 1.3 关键选型

| 选项 | 选择 | 理由 |
|---|---|---|
| Web / 桌面 / 移动 | **Web（浏览器）** | 三种模式共用一套 UI，热座与联机切换成本低，分发最轻量 |
| 语言 | **TypeScript 全栈** | 核心规则、前端、AI、服务器共用类型与数据结构，减少转换层 |
| 包管理 | **pnpm workspace** | 模块拆分清晰，本地/AI/联机代码可独立演进 |
| 网络层 | **原生 WebSocket（`ws`）+ JSON 动作协议** | 状态同步简单、可回放、易调试，无需引入复杂游戏框架 |
| 状态持久化 | **内存 + 动作日志（Action Log）** | 断线重连靠日志回放；后续可扩展落盘 |

## 2. 规则范围

### 2.1 首版完整实现的内容

#### 2.1.1 核心流程

1. **设置阶段**
   - 战争标记放在版图中央（位置 0）。
   - 4 枚军事代币正面朝上放到对应位置。
   - 10 枚发展标记洗匀后随机抽取 5 枚正面朝上放到版图，其余移出游戏。
   - 每位玩家获得 7 金币。
   - **奇迹选择**：12 张奇迹洗匀，先翻 4 张，先手 1→后手 2→先手 1；再翻 4 张，后手 1→先手 2→后手 1。每人最终 4 张奇迹。
   - 每个时代牌堆移除 3 张（不见）；时代 III 牌堆加入 3 张随机行会卡。
2. **三时代轮抽**
   - 每个时代开始时，将对应 20 张牌按固定牌阵摆放，部分正面朝上、部分正面朝下。
   - 玩家轮流拿取一张“可拿取”的牌（没有被其他牌压住）。
   - 每回合必须从拿取的牌上执行且仅执行一个动作：建造建筑、弃牌换金、建造奇迹。
   - 奇迹的“再次行动”效果在 reveals 新牌后立刻执行；若某个时代结束时触发再次行动，则该效果作废。
3. **资源与金币经济**
   - 资源不消耗，永久可用。
   - 金币支付建筑/奇迹的硬币成本，或向银行购买缺失资源。
   - 贸易公式：`单资源价格 = 2 + 对手棕色/灰色卡牌上该资源符号数量`。黄色卡与奇迹产生的资源不计入贸易价格。
   - 部分黄色卡可将特定资源（如石材、木材、黏土）的贸易价格改为 1 金币/个。
   - 弃牌收益：`2 + 自己黄色建筑数量` 金币。
4. **战争旗与冲突指示物**
   - 红色卡与部分奇迹提供战争盾，建造时立即将冲突标记向对方首都移动对应格数。
   - 冲突标记进入新版块时，触发该版块军事代币（对手失去 2 或 5 金币，不足则全失），然后代币移出游戏。
   - **军事压制胜利**：冲突标记进入对方首都所在格，立即获胜。
5. **科技符号与发展代币**
   - 7 种科技符号：齿轮、石板、罗盘、药瓶、天象仪、角尺、法律（仅 Law 代币）。
   - 每获得一对相同科技符号，立即从版图 5 枚发展标记中选择 1 枚拿走。
   - **科技压制胜利**：集齐 6 种不同科技符号，立即获胜。
   - 10 枚发展标记效果需全部实现（见 2.1.3）。
6. **奇迹建造与效果**
   - 拿一张时代卡，支付奇迹的资源/金币成本，将该时代卡翻面放到奇迹下方。
   - 全场最多建造 7 座奇迹；当第 7 座建造完成时，最后 1 张未建造的奇迹立即移出游戏。
   - 12 张奇迹效果需全部实现（见 2.1.3）。
7. **三种胜利判定**
   - 军事压制、科技压制：即时结算，游戏立即结束。
   - 终局计分：时代 III 结束后未触发即时胜利，则统计 VP。
   - 终局 VP = 军事 VP（0/2/5/10）+ 建筑 VP（蓝/黄/绿/紫）+ 奇迹 VP + 发展 VP + 金币每 3 枚 1 VP。
   - 平局：蓝色建筑 VP 高者胜；再平则共享胜利。

#### 2.1.2 时代牌阵（数据来源）

| 时代 | 牌阵结构 | 初始可拿取牌数 |
|---|---|---|
| 时代 I | 从下到上 6 / 5 / 4 / 3 / 2 共 20 张 | 底部 6 张 |
| 时代 II | 菱形结构，共 20 张 | 顶部 2 张 |
| 时代 III | 菱形结构，共 20 张 | 顶部 3 张 |

> 牌阵中每张牌被哪些牌压住、揭开条件，全部用数据文件描述，不由代码硬编码。

#### 2.1.3 需完整数据化的对象

| 对象 | 数量 | 关键属性 |
|---|---|---|
| 时代 I 建筑卡 | 23 | 名称、颜色、费用、效果、连锁符号 |
| 时代 II 建筑卡 | 23 | 同上，含“免费建造条件” |
| 时代 III 建筑卡 | 20 | 同上 |
| 行会卡 | 7 | 名称、费用、即时金币效果、终局 VP 条件 |
| 奇迹卡 | 12 | 名称、费用、效果、VP、战争盾 |
| 发展标记 | 10 | 名称、效果类型、VP |
| 军事代币 | 4 | 触发位置、对手失金 |

| 不做 | 原因 |

| **原生移动 App / 桌面客户端** | Web 版本已覆盖三种模式 |
| **原创美术资源再分发** | 版权原因，使用占位图或自绘图标；规则 PDF 保留不改动 |

## 3. 模块拆分

### 3.1 总体架构

```text
┌─────────────────────────────────────────────────────────────┐
│                       入口层（Entry Points）                   │
│  ┌──────────┐  ┌──────────┐  ┌──────────────────────────┐  │
│  │ 本地热座  │  │ 人机对战  │  │        联机对战           │  │
│  │ Local UI │  │ Local UI │  │  Web UI  ↔  Server ↔ Web │  │
│  └────┬─────┘  └────┬─────┘  └──────────────────────────┘  │
│       │             │                                        │
│       └─────────────┴────────────────┐                       │
│                                      ▼                       │
│              ┌────────────────────────────────┐             │
│              │      对战源适配层（Source Adapter） │             │
│              │  LocalSource / AISource / NetworkSource │     │
│              └────────────────────────────────┘             │
│                                      │                       │
│                                      ▼                       │
│              ┌────────────────────────────────┐             │
│              │     公共规则引擎（Core）           │             │
│              │  state machine / validator / resolver      │  │
│              │  scorer / action log / replay              │  │
│              └────────────────────────────────┘             │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 入口层差异

| 模式 | 对战源 | 谁是当前玩家 | 对手动作来源 |
|---|---|---|---|
| 本地热座 | `LocalSource` | 同一设备上的两名玩家轮流点击 | 同机另一玩家 |
| 人机 | `AISource` | 玩家 vs AI | AI 在本地计算后产生动作 |
| 联机 | `NetworkSource` | 两名玩家各自设备 | 通过网络接收服务器广播 |

### 3.3 公共规则引擎（核心复用）

引擎只暴露纯函数接口，不依赖 UI、网络、AI：

| 模块 | 职责 | 入口示例 |
|---|---|---|
| `gameSetup` | 根据随机种子生成完整初始状态 | `setup(seed)` |
| `getLegalActions` | 返回当前状态下某玩家的所有合法动作 | `getLegalActions(state, player)` |
| `applyAction` | 应用一个动作，返回新状态 + 副作用事件 | `applyAction(state, action)` |
| `resolveCost` | 计算建造费用，含贸易价格与折扣 | `resolveCost(state, player, cost)` |
| `checkVictory` | 检查即时胜利与终局胜利 | `checkVictory(state)` |
| `scoreGame` | 时代 III 结束后计分 | `scoreGame(state)` |

### 3.4 适配层隔离差异

| 差异点 | 适配层处理 |
|---|---|
| 输入来源 | `SourceAdapter.nextAction(state)` 统一返回 `Promise<Action>` |
| 状态展示 | 本地模式直接渲染完整状态；联机模式仅渲染服务器同步后的状态 |
| 隐藏信息 | 本地热座可见全部；AI 按难度决定是否读取隐藏信息；联机客户端只接收可见状态 |
| 等待/提示 | 本地模式等待玩家点击；人机模式显示“AI 思考中”；联机模式显示“等待对手” |
| 断线恢复 | 仅 `NetworkSource` 实现断线重连与日志追赶 |

## 4. 数据与状态设计

### 4.1 数据描述方式

所有卡牌、奇迹、代币、牌阵均用 JSON / YAML 描述，便于校对与热更新：

| 数据文件 | 内容 |
|---|---|
| `data/cards.json` | 全部时代卡与行会卡（ID、名称、时代、颜色、费用、效果、连锁符号） |
| `data/wonders.json` | 12 张奇迹（ID、名称、费用、效果列表、VP、战争盾） |
| `data/progressTokens.json` | 10 枚发展标记（ID、名称、效果、VP） |
| `data/militaryTokens.json` | 4 枚军事代币（触发位置、对手失金） |
| `data/structures.json` | 三个时代的牌阵拓扑（每张卡被哪些卡压住、初始是否正面朝下） |
| `data/militaryTrack.json` | 军事轨道 19 格 + 首都、区块边界、VP 档位 |

> **数据录入原则**：以 `7-Wonders-Duel-Rules-US.pdf` 与参考卡为基准；`Complete_Reference_Sheet_V4.pdf` 中 Pantheon / Agora 相关条目需剔除。

### 4.2 对局状态（GameState）

采用单一不可变状态树，任何动作都产生新状态，便于回放与调试：

```text
GameState
├── meta
│   ├── gameId
│   ├── seed          // 用于复现随机过程
│   └── rngState      // 可选：记录伪随机状态
├── phase             // setup | wonderDraft | age | betweenAges | gameOver
├── age               // 1 | 2 | 3
├── turnPlayer        // 当前行动玩家
├── players[2]
│   ├── city
│   │   ├── buildings[color][]
│   │   ├── wondersBuilt[]
│   │   ├── wondersUnbuilt[]
│   │   ├── scienceSymbols[]
│   │   ├── progressTokens[]
│   │   └── tradeDiscounts
│   ├── coins
│   └── militaryStrength
├── structure
│   ├── slots[]       // { cardId, faceDown, revealed, accessible, taken }
│   └── remainingCount
├── board
│   ├── conflictPawnPosition
│   ├── militaryTokensRemaining[]
│   └── progressTokensAvailable[]
├── discardPile[]
├── actionLog[]       // 按顺序记录所有动作，回放唯一来源
└── pendingChoices    // 需等待玩家选择的交互式效果（如 Great Library 选发展标记）
```

### 4.3 玩家动作定义

所有动作统一为 JSON 对象，被三种模式共用：

| 动作类型 | 触发时机 | payload 示例 |
|---|---|---|
| `DRAFT_WONDER` | 奇迹选择阶段 | `{ wonderId }` |
| `CHOOSE_START_PLAYER` | 时代间切换且军事平手 | `{ nextPlayer }` |
| `SELECT_CARD` | 玩家点击牌阵 | `{ slotIndex }` |
| `BUILD_CARD` | 选择建造建筑 | `{ slotIndex }` |
| `DISCARD_CARD` | 选择弃牌换金 | `{ slotIndex }` |
| `BUILD_WONDER` | 选择建造奇迹 | `{ slotIndex, wonderId }` |
| `BUY_RESOURCE` | 需要买资源时 | `{ resources: { wood: 1 } }` |
| `CHOOSE_PROGRESS_TOKEN` | 凑成科技对或 Great Library | `{ tokenId }` |
| `CHOOSE_DISCARDED_CARD` | Mausoleum 效果 | `{ cardId }` |
| `CHOOSE_OPPONENT_CARD` | Circus Maximus / Statue of Zeus | `{ cardId }` |
| `CHOOSE_DISCARDED_WONDER` | 非基础规则，预留 |

### 4.4 关键状态迁移与合法性校验点

| 阶段 | 校验点 | 非法时处理 |
|---|---|---|
| 奇迹选择 | 按 1-2-1 / 1-2-1 顺序选择；牌必须在桌面上 | 拒绝动作，提示错误 |
| 拿牌 | 目标槽位 `accessible && !taken` | 拒绝 |
| 建造建筑 | 玩家持有该牌；费用可支付（资源+金币+贸易+连锁）；未达胜利前 | 拒绝并提示缺多少资源/金币 |
| 弃牌 | 玩家持有该牌 | 拒绝 |
| 建造奇迹 | 玩家持有未建奇迹；费用可支付；全场奇迹 < 7 | 拒绝 |
| 奇迹再次行动 | 若本时代牌阵已空，效果作废 | 自动跳过 |
| 军事移动 | 每移动一格检查是否进入新区块或首都 | 自动触发代币/即时胜利 |
| 科技对 | 获得一对后必须选 1 枚可用发展标记 | 进入 `pendingChoices` 等待 |
| 时代结束 | 检查军事强弱决定下一时代起始玩家；平手由最后行动玩家选择 | 进入选择状态 |
| 终局 | 时代 III 无即时胜利则执行 `scoreGame` | 生成最终状态 |

## 5. 人机（AI）

### 5.1 AI 决策输入

| 信息类型 | 是否可见 | 说明 |
|---|---|---|
| 双方城市、金币、奇迹、发展标记 | 可见 | 公开信息 |
| 牌阵中已翻开的牌 | 可见 | 公开信息 |
| 牌阵中正面朝下的牌 | **隐藏** | 时代 I/II 中尚未揭开 |
| 每时代移除的 3 张牌 | **隐藏** |  setup 时移出 |
| 时代 III 混入的 3 张行会卡 | **隐藏** | 直到翻开 |
| 对手手牌/未建奇迹 | 可见 | 基础规则无手牌概念，奇迹公开 |

### 5.2 评估函数考虑因素

AI 评估当前状态优劣时，综合以下指标（权重随难度调整）：

| 因素 | 说明 |
|---|---|
| 即时 VP | 当前已得 VP（军事 + 建筑 + 奇迹 + 发展 + 金币折算） |
| 金币与购买力 | 当前金币、每回合收入、资源覆盖度 |
| 军事压力 | 冲突标记位置、是否接近压制/被压制、下一块军事代币价值 |
| 科技进度 | 科技符号种类数、对子数、距离科技压制差值 |
| 资源引擎 | 棕色/灰色/黄色资源是否完整、贸易依赖度 |
| 连锁潜力 | 下一时代可免费建造的建筑数量 |
| 奇迹可行性 | 未建奇迹的剩余资源缺口、奇迹效果价值 |
| 发展标记价值 | 代币效果与当前策略匹配度 |
| 牌阵控制 | 拿某张牌是否会为对手暴露强牌 |

### 5.3 1–3 档难度差异

| 难度 | 算法 | 思考深度 | 隐藏信息处理 | 特点 |
|---|---|---|---|---|
| **简单** | 贪心启发式 | 1-ply | 忽略隐藏牌 | 只选当前评估分最高的动作，偶有低级失误 |
| **中等** | Minimax + Alpha-Beta | 2–3 ply | 用可见信息 | 考虑对手一步回应，会阻止科技/军事即时胜利 |
| **困难** | MCTS / Expectimax | 5+ ply 或固定模拟次数 | 对隐藏牌做蒙特卡洛采样 | 会算连锁、会囤资源、会卡对手暴露牌 |

### 5.4 响应节奏与“思考中”表现

| 场景 | 设计 |
|---|---|
| 简单 | 几乎立即出招（< 200 ms），无思考动画 |
| 中等 | 300–800 ms，显示简短“AI 思考中…” |
| 困难 | 1–3 s（可配置），带进度条或“AI 正在推演”提示 |
| 异步 | AI 在 Web Worker / 独立线程计算，避免阻塞 UI |
| 可取消 | 仅在玩家回合可操作；AI 思考中不可取消已提交的 AI 动作 |

## 6. 联机

### 6.1 房间与匹配流程

| 步骤 | 说明 |
|---|---|
| 创建房间 | 房主生成 6 位房间码，服务器创建 Room，等待玩家 2 |
| 加入房间 | 玩家输入房间码加入，人满后进入准备界面 |
| 选边/随机 | 首版由服务器随机决定先手；后续可增加选边 |
| 开始游戏 | 房主点击开始，服务器生成 seed 并广播初始状态 |
| 观战 | 首版暂不支持；后续可扩展 |

### 6.2 同步策略

| 策略 | 选择 | 理由 |
|---|---|---|
| 权威归属 | **服务器权威** | 防作弊、防双方状态分叉 |
| 同步粒度 | **动作级同步** | 客户端发送动作，服务器验证后广播；日志天然形成 |
| 状态广播 | 同时发送 `statePatch` + `lastAction` | 新客户端可追日志，老客户端可用 patch 快速更新 |
| 乐观反馈 | 仅本地 UI 高亮，不立即改变权威状态 | 避免网络延迟导致的状态回滚视觉冲突 |

### 6.3 断线重连与延迟处理

| 问题 | 方案 |
|---|---|
| 短时断线 | 服务器保留房间与最新状态 5 分钟；重连后发送 `actionLog` 缺失部分 |
| 长时断线 | 房间标记为“等待重连”，另一玩家可返回大厅或等待 |
| 动作丢失 | 客户端发送动作带 `clientActionId`，服务器去重；超时未确认则重发 |
| 高延迟 | 使用动作日志而非实时状态差帧；对手动作到达后平滑动画补间 |
| 作弊/篡改 | 服务器校验所有 `applyAction`；客户端状态仅用于渲染 |

### 6.4 与本地模式共用的动作协议

```text
客户端 → 服务器
{
  type: "ACTION",
  roomId: "123456",
  clientActionId: "uuid",
  action: { type: "BUILD_CARD", slotIndex: 3, player: 0 }
}

服务器 → 客户端
{
  type: "STATE_UPDATE",
  action: { type: "BUILD_CARD", slotIndex: 3, player: 0 },
  state: { /* 完整或增量状态 */ },
  logIndex: 17
}
```

> 同一 `Action` 类型定义在 `packages/core` 中，前端、AI、服务器共用。
